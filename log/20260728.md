# 28 Jul 2026 – DeepSeek 3 Expert – Physical product design, Shabbat Lock, and manual outline

_HebrewClock, Documentation_

No code was written, no console was opened. The session was a pure product‑design detour that took the working JavaScript clock and asked: what does this actually become in someone’s hands? By the end, we had a full SKU matrix, a detailed hardware specification, a complete user‑manual skeleton, and the academic dial’s visual language locked down for print.

### Product SKUs and physical form factors

The conversation began with a simple question: “Let’s discuss the possible implementations of this, different SKUs.” Four base form factors for the pure clock emerged quickly:

* Wall clock – round or square, largest display (20×20 cm), four 18650 battery slots for extended backup.
* Desktop clock – medium (13×13 cm), two slots.
* Bedside clock – smaller (9×9 cm), two slots, sleep‑mode capable.
* Travel/Bag clock – smallest (6×6 cm), one slot, pocketable.

A wristwatch category was added separately, using a MIP display with an integrated battery. Later, two further display‑oriented forms were introduced: the Info Panel (15″ rectangular, showing clock plus ambient data like date, zmanim, Torah portion) and two HDMI sticks — one for a pure clock face on a TV, one for the info‑panel layout. The complete matrix covered eight distinct form factors, with display technology (TFT, LCD, OLED, e‑paper) as a per‑SKU column and battery as an optional add‑on.

### Hardware specifications

Every clock, regardless of size, shares the same core hardware DNA.

* USB‑C provides power, battery charging, and firmware updates. There is no power button; the device boots when USB or batteries are connected.
* Batteries are user‑supplied 18650 Li‑ion cells. The number of slots varies, but the user can fill any number up to the maximum. The batteries are purely a backup — a UPS — and the Institute publishes runtime estimates based on genuine reference cells (Samsung, Sony). The rule is simple: identical cells, same charge level, genuine brands only. “Batteries are your problem — but we explain the rules.”
* GPS provides time and location synchronisation. The module is a u‑blox NEO‑M8N with an optional active antenna, auto‑detected via current sensing. GPS is only activated on manual trigger or wake‑from‑sleep, and never automatically; the user is always in control. The RTC (DS3231 or RV‑3028) holds time with millisecond drift between syncs.
* BLE is used for firmware updates. Wi‑Fi is deliberately absent, even if the chip (e.g., ESP32‑S3) includes it — a concession to Haredi sensitivity to “Wi‑Fi.”
* A buzzer provides future zmanim chimes, Shabbat alerts, low‑battery warnings, and encoder feedback.
* The interface is a single encoder (rotate to browse, push to select) plus a dedicated “back” button. This identical control scheme spans all SKUs.

Display options were evaluated: TFT (affordable, poor outdoors), LCD (better indoors), OLED (vibrant, dark‑room friendly), and e‑paper (ultra‑low power, daylight perfect, but requires a front‑light at night). E‑paper variants lose smooth animation and the seconds hand; the seconds hand steps once per seasonal minute, and bands update at the same interval. Both TFT and e‑paper were priced equivalently — the choice is about usage style, not cost.

### User interface and interaction model

In normal view the encoder does nothing; a short press toggles between the civil dial (default) and the academic dial. A long press enters a two‑level settings menu:

* Level 1 lists setting categories (Gra/Ma, Dawn, Nightfall, Misheyakir). Rotating highlights a category, a description is displayed, and pressing enters Level 2.
* Level 2 shows the list of values for that category, with the currently active value highlighted. Rotating previews each option, with a description explaining it. Pressing commits the selection and returns to Level 1; the back button discards the preview and returns.

This ensures no accidental changes — the user browses before committing, and the back button always means “back.”

Portable SKUs (Bedside, Travel, Wristwatch) support sleep: the display turns off after a fixed timeout (initially 20 seconds). Any input wakes the device, but the first input is consumed by the wake‑up event and does not toggle views or enter menus. A MEMS microphone on the Bedside and Wall clocks allows clap‑wake.

### Shabbat Lock – core halachic design

Shabbat Lock is mandatory, always enabled, and non‑negotiable for the strict‑observance line. When Shabbat begins, the device automatically disables all physical inputs and GPS reception, prevents low‑power sleep so the display remains always‑on but completely non‑interactive, and re‑enables everything after Shabbat ends.

A special case was designed for first‑ever power‑on during Shabbat. If the RTC is zero and the device is powered up on Shabbat, it briefly activates GPS to obtain the time, sets the RTC, shuts GPS off, detects Shabbat, and immediately enters lock mode — no screen, no buttons. The RTC is set once as a consequence of the user’s initial power application, preventing repeated mistakes. The user action of inserting batteries or connecting USB is the melacha; the device mitigates damage by not becoming interactive and by preventing further melacha.

At the moment Shabbat enters, the device captures the current GPS position as the halachic place of dwelling, which is frozen for the duration of Shabbat. The manual advises users to be at their dwelling place at that instant.

Two market versions were defined: Strict (Shabbat Lock always on, no option to disable) and Standard (user‑enablable feature). The manuals differ only in how the lock is described — no community labelling, just “strict observance.” An internal `STRICT_MODE` flag controls the behaviour.

### Product matrix and naming

The naming convention locks in “Hebrew Clock” as the product line name, with the form factor and display technology in parentheses: Hebrew Clock Wall (oled), Hebrew Clock Travel (e‑paper). The wristwatch is simply Hebrew Clock Wristwatch. Info Panels and HDMI sticks follow the same pattern: Hebrew Info Panel (tft), Hebrew Clock HDMI. Display suffixes are lowercase: (tft), (lcd), (oled), (e‑paper).

Sizes were fixed: Wall 20×20 cm, Desktop 13×13 cm, Bedside 9×9 cm, Travel 6×6 cm, Info Panel 15 inch.

### User manual outline

The manual was structured into three sections:

1. **The Hebrew Clock** – SKU table, physical description (USB‑C, batteries, GPS, encoder and buttons, BLE, RTC, buzzer, display).
2. **Understanding the Hebrew Day** – a scholarly primer covering the Hebrew day and night, Hebrew date, nightfall and dawn, MA vs. GRA, relative (seasonal) hours, the zmanim (each defined with halachic use), and customs and opinions (presets and individual settings, with sources).
3. **Using the Clock** – interface and operation, to be detailed later.

The manual was conceived as the central pitch — a complete scholarly guide that teaches mastery, modelled after the Commodore 64 user’s manual. Images would be generated from the same classes that run on the device, not hand‑drawn approximations. Separate Hebrew and English editions were planned.

### Academic dial visual specification

The academic clock face was documented in precise detail for the manual, broken into orientation, marks, and three concentric rings.

**Orientation**: Midnight (Chatzot HaLayla) straight up, midday straight down, sunrise left, sunset right. The night arc is a darker pie background at the bottom.

**Marks**: Four major marks for the cardinal moments (yemama start, yemama end/midday, midnight, and the opposite mid‑points), eight remaining hour marks (smaller), and twelve half‑hour marks (smallest).

**Ring 1 – Daily Zmanim Bands**: The colours were pulled directly from the JavaScript implementation: Misheyakir `#3a5a7c`, Shema `#6b8a9e`, Amidah `#a3b8c5`, a transparent noon gap, Minchah Gedolah `#7a8c6d`, Minchah Ketanah `#cbb88c`, Plag Minchah `#b08a5c`.

**Night Watches (Ashmorot)**: Two schemes were specified. The 3‑watch scheme: 1st `#3a3a3a`, 2nd `#6a6a6a`, 3rd `#9a9a9a`. The 4‑watch scheme: 1st `#3a3a3a`, 2nd `#5a5a5a`, 3rd `#7a7a7a`, 4th `#9a9a9a`. Both share the same start and end colours, with intermediates scaled evenly.

**Ring 2 – Special Days and Periods**: A system of solid colours and stripes was defined to encode the calendar:
- Shabbat / Yom Tov: solid muted red (`#a05050`).
- Chol HaMoed (weekday): solid lighter red (`#c07070`).
- Yom Kippur / Tisha B’Av: diagonal black/yellow stripes.
- Other fasts: diagonal white/black stripes (weekdays only).
- Periods (Omer, Three Weeks, Nine Days, Ten Days of Repentance) on weekdays: vertical white/silver stripes; on Shabbat: vertical white/red stripes.
- Bein HaZmanim (weekday): solid blue (`#8090b0`); on Shabbat: vertical blue/red stripes.
- Yom Kippur on Shabbat: diagonal yellow/red stripes.

The visual language rules were: solid = highest sanctity, diagonal stripes = fasts, vertical stripes = periods. The dark stripe inherits the day’s background colour (black on weekdays, red on Shabbat, blue on Bein HaZmanim).

**Ring 3 – Moon**: A yellow/amber arc (`#d4a017`), visible when the moon is above the horizon.

Missing items — national holidays, Purim, Chanukkah, and a distinct Yom Tov colour separate from Shabbat — were noted for future inclusion.

### Key philosophical decisions

Several principles were reaffirmed. The clock is a UPS device: the battery only keeps it running during a power cut; normally it is USB‑powered. Price is not a barrier — the Institute offers designs on demand and does not pre‑manufacture or hold stock; the full SKU list is a blueprint, not a catalogue. Runtime estimates are transparent and based on genuine reference batteries. BLE, not Wi‑Fi, is the connectivity choice, even if the chip supports Wi‑Fi — a deliberate decision for Haredi acceptance. The manual is a living document that will be filled in as development progresses, starting with the simplest SKU (Travel or Bedside, USB‑only, TFT).

The session ended with the clock now existing as both a software artefact and a fully specified physical product. The next steps were clear: design the manual images, port the core classes to Python for accurate rendering, refine the enclosure models, and build a prototype.
