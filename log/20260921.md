### Submodules that follow the latest

A submodule is recorded in the parent repo as an exact commit SHA, so a plain clone or pull gives that pinned commit, which is the opposite of what fonts need. What was settled: keep submodules, track a branch, and sync with `--remote`.

* Set `branch = main` in `.gitmodules` (`git submodule add -b main …` or `git submodule set-branch --branch main <path>`).
* Clone with `git clone --recurse-submodules`, then `git submodule update --remote`.
* Sync later with `git pull` and then `git submodule update --remote`. With no path, that updates every submodule.
* Don't use `submodule.recurse true`, which resets submodules to the committed pointer on every pull.
* After `--remote`, the parent shows the submodule as modified, and it only counts for other people once that is committed.

I also suggested alternatives (symlinks, a pull-at-build step, Actions), and was told to stop and just explain why not, which was right.

`Fonts-dev`'s `fonts` submodule got `branch = main` and was re-cloned with `--remote`. It was clean with nothing unpushed, and the commit went up as `1f85081..4e97003`. The push method was a one-time `Authorization` header with the token from `/root/claude.txt`, with the remote URL staying tokenless; it was rejected twice at first because of how it had been shown, and approved once explained.

### HTTPS

The copy buttons failed because the clipboard API only works in secure contexts, and the VPS was on plain HTTP. The answer was a fixed self-signed certificate with the server IP in its SAN, which is accepted once per browser (`studio-cert.pem` and `studio-key.pem` are gitignored).

Then came a stall: Flask's dev server does the TLS handshake in its single accept loop, so one idle browser connection blocked everything. It was reproduced and fixed with `tls.py`, which moves the handshake into each request thread, and it stays fast even with 5 silent connections open.

### `export.py` replaces `automate.py`

Usage is `export.py [type] psalm... [--cache]`. The types are `score` (vertical video with music), `library` (landscape, no music), `score-audio` and `library-audio`, and with no type it exports all four. It overwrites by default, and `--cache` skips files that exist, so an interrupted batch continues when restarted. No arguments, an unknown type or a psalm outside 1–150 print a usage line and exit.

My first version had `--only`, `--all`, ranges and `--force`, which were rejected as things nobody had asked for. `--force` became the default behaviour and `--cache` the opt-in. ffmpeg now writes `name.part.ext` and one `os.replace()` moves it to the final name, in `PsalmAudio.export` (tags are written to the `.part` first), `Video.export`, `EpisodeVideo.export` and `ParashahVideo.export`, so a stopped run can no longer leave a broken file that looks finished. There is no helper, just one or two lines in each place, and the `#` comments are gone, keeping the shebang and the usage docstring.

`export.py score 117` took 1m25s and produced a 720×1280 h264/aac video of 17.8 s, with no `.part` left behind, and `--cache` skipped it on the second run. Stopping a run halfway, the other three types and multi-psalm batches were not tested.

### Backgrounds

The HD preview returned a 500, because `Media.HDH` is 1920×1080 but the fog files were named `back-1280x720.mp4` and `back-720x1280.mp4`. A real HD background was needed, so the old recipe was reconstructed from the `generate_backgrounds.py` script: crop `back.mov` to the centre square, desaturate with `hue=s=0`, scale by 0.9 into `back.mp4` (972×972), then crop a centre strip in the target ratio and scale it, encoding with `libx264 -preset fast -crf 18 +faststart`. A frame rebuilt that way matched the existing file at 41 dB, while my first guess (a plain scale) gave orange footage.

`back.mov` is 1920×1080 landscape, square pixels, no rotation, 29.97 fps, 483 frames, 16.1 s, Motion JPEG (yuvj422p), about 83 Mbit/s, no audio, 167 MB. `assets/back.orig.mp4` is the desaturated full-frame version at 9.7 MB (17 times smaller), 1920×1080, 483 frames, PSNR 47.4 dB average (46.5 minimum), SSIM 0.984 against the source.

`generate-assets.py videos|covers` (renamed and split from the old script) takes no flags, and a wrong argument prints usage. `videos` builds `back.mp4`, `back-720x1280.mp4`, `back-1280x720.mp4` and the new `back-1920x1080.mp4` from `back.orig.mp4`; `covers` extracts the jpg stills (`back*.jpg` and one `NNN.jpg` per psalm mp4). Compared with the old script it has a new source, no `hue` step (already gray), the HD target, no overwrite flag, and the split, and the HD file is cropped from the full-resolution square (skipping the 0.9 scale), so it has the same framing but is sharper.

A full run over the real `assets/` matched the four old videos at 46.8–47.6 dB. It also rewrote 37 jpgs (31 psalm frames, differing only by JPEG noise), which were restored with `git checkout`, since the covers were already generated. I first thought the 1280×720 file wasn't needed, and was corrected: the parashah video for TikTok will be landscape SD, so all four stay.
