# 24 Aug 2026 – DeepSeek Expert, Claude Sonnet 5, Gemini 3, Qwen‑3.8‑Max – Suno archive: bulk download, metadata sync, and the policy‑change panic

*Code, Media, Web*

The session began with a deadline and a warning: from 3 September 2026, Suno would restrict downloads to almost nothing. We had generated 1,636 tracks and 2,239 stems on a paid Pro plan, spread across 15 workspaces — background music for Psalms, Piyutim, and other Institute projects. If we did not act, years of generated material would become inaccessible. The goal was non‑negotiable: get every MP3 and every stem onto local disk before the policy changed, and preserve the metadata needed to keep the library organised.

### Early attempts from the browser console

We started on Android using Kiwi Browser’s DevTools console. The first discovery was that Suno exposes an internal API at `POST https://studio-api-prod.suno.com/api/feed/v3`, but it rejected requests without a `Browser-Token` anti‑bot header and a fresh `Authorization: Bearer` token. We learned that `window.Clerk.session.getToken()` returns a valid token, and that the CDN (`cdn1.suno.ai`) does not require credentials if the request omits `credentials: 'include'`.

Automated collection still failed. Pasting live JWT tokens into chat was recognised as a security risk, and the console scripts triggered 401s and CORS errors. The path forward was not yet clear.

### Manual JSON page saving

As a fallback, we moved to a manual but safe method. While logged in, we copied each page’s JSON response from the Network tab and pasted it into a `prompt()` box in the console, saving it as `01.json`, `02.json`, etc. This worked but was slow. At one point, about 20 of the expected 47 pages had been saved for the default workspace. The files were processed later in Termux.

This manual phase produced the raw clip metadata, but it could not scale to 15 workspaces and thousands of clips.

### Automated workspace collection

Eventually the API path was made reliable from the browser console. Two functions were built:

- `getWorkspaces()` fetches `GET https://studio-api-prod.suno.com/api/project/me` and saves `workspaces.json`. It builds a `window.__projectIds` map dynamically from the response, so no hardcoded project IDs are needed.
- `collect(projectName)` calls the feed endpoint with cursor pagination and workspace filters, and downloads each workspace’s clips as `<projectName>.json`.

This replaced the manual page saving. All 15 workspaces were collected. The `getWorkspaces()` function was de‑hardcoded so that the project ID map is derived from the live API response, avoiding brittle hardcoded entries.

### Combine and inventory scripts

With per‑workspace JSON files in hand, `combine.py` read `workspaces.json` and merged all `<projectName>.json` files into a single `json/out.json`, deduplicating by clip ID. The local archive was now keyed by **ID**, not by title or workspace — a decision that later proved essential.

`ids.py` generated `ids.js` with missing‑file lists by comparing `out.json` against the local directories:

- `library` — tracks grouped by project name
- `stems` — stem IDs whose MP3s were missing from `stems/`
- `images` — tracks missing cover images from `jpg/`
- `mp3` — tracks missing MP3s from `mp3/`

No existing file was ever re‑downloaded. The scripts only identified gaps.

### Flask browser app

A read‑only Flask app was built to inspect the archive. `app.py` loaded `json/out.json` and `json/workspaces.json`, computed on‑disk coverage, and rendered workspace stats. Templates were split into `base.html`, `index.html`, `workspace.html`, and `track.html`, with a dark theme in `styles.css`. The main page showed per‑workspace track, stem, and MP3 coverage; workspace pages listed clips with cover thumbnails and durations; track pages showed the raw JSON.

The app became the visual dashboard for the backup process.

### Download phase

Browser functions in `suno.js` downloaded missing files:

- `download_missing_mp3()` — random MP3 via `https://cdn1.suno.ai/<id>.mp3`
- `download_missing_stem()` — same CDN, stem IDs
- `download_missing_images()` / `download_missing_image()` — cover images via `https://cdn2.suno.ai/image_<id>.jpeg`

The download lists came from the arrays generated by `ids.py`. By the end, every track and stem was present locally. The final totals: **1,636 tracks (100%)**, **2,239 stems (100%)**, roughly 5 GB of tracks and 7 GB of stems.

### The stats‑table crisis

The most painful part of the session was the Flask stats table. The symptom was impossible: global MP3 showed 100%, while several workspaces showed 0%. Multiple assistants failed repeatedly — hardcoding percentages, using self‑division (`total / total * 100`), mixing categories, and adding defensive `continue` statements that skipped stems whose parent track was not found.

The correct fix required real on‑disk checks against `os.listdir("mp3")` and `os.listdir("stems")`, and proper per‑workspace mapping using each stem’s own project metadata. Once corrected, per‑workspace sums matched global totals exactly. The `default` fallback was later changed to `"My Workspace"` to reflect the real workspace structure.

### M4A detour

The API JSON contained CloudFront URLs for `.m4a` files. We downloaded two test files; both were corrupted and not valid audio — ffprobe found no MP4 header. All M4A logic was stripped from `app.py`, `ids.py`, `download.js`, and the templates. The final archive contains only MP3s, stems, and images.

### Image download issues

Image downloads from `cdn2.suno.ai` hit 403 errors, likely due to referrer/session issues or an incorrect URL pattern for some IDs. The image functions were retained but image completeness was not as critical as audio. The archive remains functional without cover images.

### Cleanup and final architecture

`getWorkspaces()` was made dynamic, `collect()` read from `window.__projectIds`, and all comments and blank lines inside functions were stripped. The local files remained flat: `mp3/<id>.mp3`, `stems/<id>.mp3`, `jpg/<id>.jpg`. The metadata in `out.json` stores titles, workspaces, and timestamps, so titles can be reorganised on Suno without affecting local files.

The final architecture was:

- `json/` — per‑workspace JSON files, `workspaces.json`, and combined `out.json`
- `mp3/` — track MP3s
- `stems/` — stem MP3s
- `jpg/` — cover images
- `combine.py` — merges workspace JSONs into `out.json`
- `ids.py` — generates missing‑file lists
- `app.py` — Flask browser
- `suno.js` — browser collection and download functions

### State at session end

The archive is complete. Every MP3 and stem generated on Suno is local. The metadata is stored in `out.json` and can be resynced by re‑running the collection scripts until the API changes. New tracks created after the policy change can be downloaded in small batches, fitting within the new limits. The audio is safe; the only long‑term risk is metadata drift once the API changes, but for now we have until 3 September to run final checks.

The session was messy, with repeated assistant failures and a stats bug that consumed far too much time, but the final state is exactly what we set out to achieve: a local, ID‑keyed archive that no platform policy can take away.
