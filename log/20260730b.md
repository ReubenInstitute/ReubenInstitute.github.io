### MCU selection and display interface

The choice of microcontroller was forced by a single hard requirement: the display must be driven by a parallel interface. Smooth animations — the spring‑loaded band sliding, the face‑swap between civil and academic dials — demand high throughput and low latency, which SPI cannot reliably deliver on a 480‑pixel‑wide panel. The user’s 4‑inch ILI9486 parallel TFT became the reference, and the MCU had to speak 8080‑parallel natively.

Three candidates were examined. The STM32WB55 offered built‑in BLE with no Wi‑Fi, ideal for Haredi acceptance, but it lacks a parallel LCD controller — it was rejected. The ESP32‑S3 has a native 8080‑parallel LCD interface and BLE, but also includes Wi‑Fi hardware, which is a political and religious liability even if the firmware never enables it. The final recommendation was an STM32F4 or F7 with FSMC for the parallel display and an external BLE module, such as the nRF52840, to keep Wi‑Fi entirely absent from the board. The RTC choices were confirmed as DS3231 for common availability or RV‑3028 for ultra‑low‑power accuracy.

### Shabbat Lock as hardware behaviour

The Shabbat Lock, already designed at the UX level, was translated into electrical terms. The device has no power button — it boots when USB or batteries are applied. At boot, if the RTC indicates Shabbat, the MCU briefly powers the GPS to obtain a time fix, writes the RTC, shuts down the GPS, and then enters a locked state with the display off and all inputs disabled. The display stays dark for the remainder of Shabbat; it does not keep the screen on, because that would constitute an active melacha‑like state. The display would be dark during Shabbat, not always on, to avoid the halachic issue of maintaining an active display. Actually, after reviewing the manual wording, the display is kept always‑on but non‑interactive; the clock face remains visible so it can be read passively, but no touch, button, or movement changes anything. We clarified that the display remains on, but the device does not respond to any input. The GPS location is frozen at the moment Shabbat enters; that location becomes the halachic place of dwelling until Shabbat ends.

The two market versions — Strict (always enabled) and Standard (user‑enablable) — were maintained, with an internal `STRICT_MODE` flag that, when true, prevents the lock from ever being disabled.

### Display buffer and drawing primitives

The first piece of actual firmware code was written: a `Display` class with a public `uint8_t buffer[WIDTH * HEIGHT * 3]` — raw RGB 24‑bit, no getters, no STL, no heap allocation. The dimensions were hardcoded to 240×240 for initial testing, matching the JavaScript demo resolution.

Three drawing primitives were implemented with distance‑field antialiasing:

- `drawLine(x1, y1, x2, y2, thickness, color)` — a straight line with a 2‑pixel antialiasing ramp around the ideal edge, blending directly into the RGB buffer.
- `drawArc(cx, cy, radius, startAngle, endAngle, thickness, color)` — a stroked circular arc using the same antialiasing.
- `drawCircle(cx, cy, radius, thickness, color)` — a convenience wrapper that calls `drawArc` with a 0–360° sweep.

A `fill(color)` method clears the buffer, and a `pointToSegmentDistance` helper handles the distance calculations. No `min`, `max`, or `clamp` functions were written; all comparisons were inlined.

### Civil clock rendering

A `Clock` class was built that holds a reference to a `Display` and exposes an `update(DateTime)` method. The civil dial rendering followed the JavaScript original exactly:

- Cream background (`0xFAF0E6`).
- Minute ticks: thin grey lines every 6°, skipping positions occupied by hour ticks.
- Hour ticks: thick dark lines, length 16 px, with cardinal hours (12, 3, 6, 9) at 32 px.
- Hands: hour, minute, and second hands, with lengths and colours matching the JS clock.
- Centre cap and a dial rim drawn last.

Hand angles were computed identically to the JavaScript — no invented offsets, no 90° twists. A test program output a `civil_clock.png` and the result matched the browser version pixel‑for‑pixel.

### Hebrew clock rendering

The `HebrewClock` class took a `Display&` and a `const LocalHebrewDate&`, with an `update(float seasonalHour)` method. The first several attempts were disastrous. Wrong 90° and 270° offsets were introduced, coordinate systems were mixed, and the clock rendered upside down or with hands pointing into empty space. The user became justifiably frustrated and demanded a direct, literal translation of the JavaScript angle formulas with no reinterpretation.

The correct approach used the JavaScript formulas verbatim:

- For night hours: `angle = 180 - nightArc/2 + (h/12) * nightArc`
- For day hours: `angle = -dayArc/2 + ((h-12)/12) * dayArc`

These angles have 0° at the top and increase clockwise. The drawing mapping is `x = cx + length * sin(angleRad)`, `y = cy - length * cos(angleRad)`. The night background is a filled grey arc spanning the night duration. Twenty‑four hour ticks are drawn, each placed at the start of its hour, with day ticks in grey and night ticks in a lighter shade. The hour hand and second hand are drawn, and the second hand sweeps within the current seasonal hour.

After several rounds of correction, the Hebrew clock rendered correctly, matching the JavaScript dial exactly, including the correct day/night arc proportions for the given location and custom.

### Build system

The Makefile was extended with a `test` target that compiles and links `Display.o`, `Clock.o`, and all calendar library objects. `stb_image_write.h` was used for PNG output — a single public‑domain header, no additional dependencies. The test program generates both `civil_clock.png` and `hebrew_clock.png`.

### Session dynamics

The session was a study in the cost of over‑translation. The AI repeatedly added abstractions, renamed constants, and introduced “clever” angle transformations that broke the rendering. The user’s insistence on minimal, literal translation — no added methods, no getters, no STL, no invented angles — ultimately forced the code back to correctness. The final apology and corrected code matched the JavaScript class exactly, and the lesson was clear: the reference is the reference, and a port is not an opportunity for improvement.
